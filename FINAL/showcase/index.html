What I automate, and how I decide

I write the spec, a coding agent builds, I verify the result against real data, then the automation runs and I measure it. What earns its keep stays; what does not is retired or handed back to a person.

01How I decide what to build

There is always more to automate than one person can build. So I rank by expected value. How much time or risk does it remove, how often does it run, and what does it cost to build and keep working? The method is the same whether the builder is an agent or me.

  1. Spec. One page: what done looks like, where the real data is, and what the agent may not do. Usually: invent facts, spend money, act in my name.
  2. Build. An agent builds it in its own branch or worktree. I review the design and the edge cases, not every line.
  3. Verify. Against real inputs, not a demo. I reload the page instead of trusting the DOM, and I read the saved record, not the success toast.
  4. Run. With a written run-book, so the next run does not start from zero.
  5. Measure. A number before and a number after, even a rough one. Without it I cannot tell a win from a habit.
  6. Keep, fix or retire. A task that keeps failing after a few honest attempts goes back to a person, and the run-book records why. Nobody pays for the same lesson twice.

02Case study: an agent-run job search

September 2026 onwards · designed and operated by me, built and run by Claude Code sessions

Problem

I was looking in three lanes at once: software, game development and drone software. That meant a dozen platforms, each with its own forms, closed skill taxonomies and interaction quirks, and one person to fill them. Done by hand it is slow, and the profiles drift apart: different dates, different rates, different stories.

The goal was narrower than "apply everywhere". One consistent story on every platform, a ranked list of openings worth my time, and applications that go out honestly in my name.

Design

  • Coordinator and workers. One session plans and spawns one session per platform group, each in its own git worktree. Sessions talk through cross-session messages.
  • Shared memory. A profile kit is the single source of truth: identity, links, bios, confirmed facts, and an open-questions list headed "ask Denis, do not invent". It is git-ignored because it holds private details.
  • Run-books updated after each failure. Every site quirk is appended the moment it costs an agent a retry. Examples: form state hidden in shadow DOM on Profesia, selects that silently drop on Lemon.io, a honeypot field on RemoteGameJobs. On Jobs.cz the save button only works through form.requestSubmit.
  • Rules the agents keep. I create every account myself. A session never performs an action another session was denied. No fact is invented to fill a required field; the field stays blank and goes on the open-questions list.
  • A decision database. Five scan agents each write JSON to one schema. The schema says "only listings you actually fetched" and "never invent emails, salaries or dates", and sets a 1 to 5 fit rubric. A build script merges, dedupes on URL and sorts. The board records apply, maybe or skip per listing.
  • Applying rules. Read the queue from the database, never apply to anything I have not marked. Draft the whole batch first, show me, then send. About ten a day, a follow-up after a week of silence, and the red flags on each listing are shown, not written around.

The first application batch picked 20 roles. 14 went by email with a per-company letter in the listing's language, honest about the gaps. 12 went through portals. Two stayed open because the browser extension had no permission on those domains, which is a human click, not an agent task.

The outcomes are recorded as they came. One company replied that email does not enter their process and the portal form was filled but needs my real click on Submit. One rejected within hours because they cannot hire in Slovakia. That is useful data, and it goes in the board, not in a drawer.

What it costs to run

Token use is tracked per session in the Claude usage dashboard; I do not publish the figure here. The human cost is clearer: I create accounts, answer the open-questions list, and press the buttons agents may not press. The design keeps that list short and visible, which is the point.

What I retired or handed back to a person

  • Hitmarker avatar upload. Five attempts, each one reported "Saved", none persisted, no error anywhere. The notes conclude it is the site's own pipeline and mark it manual. Retired.
  • Contra hourly-rate dropdown. A portal combobox that dropped the selection under real clicks, JS clicks and keyboard. "Left for Denis; it is one dropdown." Handed back.
  • Upwork publishing. Blocked on a street address, a fact only I can supply. The portfolio and job alerts behind it are listed as blocked work, not skipped work.
  • Wellfound region sub-filter. Automation failed three ways. One manual click left, written down as such.
  • Arc.dev resume upload. No file input in the DOM, so it cannot be automated. The agent found that a LinkedIn link satisfies the same rule and moved on.

What I would do differently

  • Sync is a requirement, not a nicety. My apply or skip decisions were made on my phone and mirrored to local storage, so they never reached the shared database. The first batch was picked by fit score instead of from my queue.
  • Log before sending, not after. One application went out twice (the ATS deduplicated it), and one role title was never recorded. The applying agent now needs a write-to-log step before the send.
  • Verify the artifact, not the process. A PDF printed from a local file carried two dead links, and 14 emails had already gone. Now the link annotations are checked before any send.
  • Shared memory must travel. The untracked kit did not propagate into worktrees and was copied by hand. Next time it is tracked, with secrets split out.

03Case study: agent workflows for B2B clients at teamday.ai

Senior Software Development Engineer · June to September 2025 · Bratislava

What the work was

teamday.ai is an AI-agents startup. I built agent workflows that automate business processes for B2B clients. I connected LLM agents to the clients' tools and data through MCP servers, scrapers and data pipelines.

What makes an agent finish the job

Most of the work was the unglamorous glue that makes an LLM finish a task instead of describing it. That means validation, retries, structured outputs, and evals on real data. An agent that sounds done and an agent that is done look identical in a demo. They only separate when you check the output against the real system.

Client names and figures belong to the clients, so there are none here.

05Measuring a CV like an automation

Before sending my CV for this role I ran it through the screeners I could get my hands on, then changed the document and ran them again. Same habit as any automation: a number before, a number after, and a note about what the number cannot see.

Every scorer agreed on direction and none was impressed: the tailored CV is still "orange" in Resume-Matcher and under 40 on its strict keyword matcher. That is fine. The scores showed me what the parsers could not read. Three of four missed the phone number, one glued two headings together, and a dash broke a date range. Those were cheap fixes.

One number went the other way on purpose. A draft scored 66 while it called a project a production system. That project was built end to end but never launched, so the claim came out and the score dropped to 62. −4 for a CV I can defend in every line is a trade I take every time.

I also had the draft read blind by a reviewer playing Epoch's COO and hiring manager. The verdict on draft one was "developer who uses agents, not yet enablement manager". This page is part of the answer to that.
